## 3. 必须写明的解释限制

H67-A 的标签是预注册协议判定，不是“硬件绝对不可达”的证明。16 个 lost true 中有
15 个的 true-eta 最近点位于 final 51 窗口的第一帧，之后持续外离；剩余 1 个
（strict125 s1008/seed23）最近点在窗口内第 5 帧。也就是说，测量窗口主要记录的是
“最近点之后 1 s 的外离”，而不是更早的接近过程。

因此当前最准确的描述是：

1. command 已朝向 goal，实际地速在最近点后朝外，说明不是 command 方向错；
2. lost 组不是低速停滞，而是以约 `2 m/s` 地速掠过捕获球后外离；
3. default 有 `7/9` 是球外近失，strict125 有 `4/7` 是球外近失，另有
   `2/9`、`3/7` 是 true eta 进球但 p_nav 未进球的薄壳失败；
4. 因 A 和 B 同时支持，且逐 run 大多给出 B，不能把结果写成“纯执行器饱和”；
5. 下一步应把窗口前移到 plane crossing 之前，分离 pre-crossing authority 与
   post-pass recovery，而不是直接换训练算法或放大 residual。

## 4. Step 7：deterministic policy vs zero-residual

按 Goal60 baseline 的 true success 为参照，candidate 丢失数量为：

| scenario | policy lost true | zero-residual lost true |
|---|---:|---:|
| default | 5 / 160 | 4 / 40 |
| strict125 | 6 / 160 | 1 / 40 |

forced zero-residual 仍丢失 default `4` 个、strict125 `1` 个 true episode，说明
residual 不是失败的充分原因。policy 的 pooled success / eta-capture 为：

| scenario | mode | success | terminal eta capture |
|---|---|---:|---:|
| default | policy | `103/160` | `80/160` |
| default | zero | `25/40` | `19/40` |
| strict125 | policy | `46/160` | `32/160` |
| strict125 | zero | `14/40` | `11/40` |

zero-residual 在 strict125 的 success 比例甚至高于 policy pooled 值，但它的 lost
true 仍然存在；因此 Step 7 不支持“residual 越大，闭环越坏”的单调解读。

## 5. 对“是否被 NoisyNet 主导”的回答

当前证据不支持 NoisyNet 主导：

1. 正式评估走 `agent.act_batch(..., evaluate=True)`，该路径设置 `sample_noise=False`；
   actor 使用 mean weights，评估轨迹中不采样 NoisyNet 噪声；
2. lost 的 command-goal cosine 为 `0.987`，没有出现噪声把 command 推离 goal 的
   特征；实际地速方向偏离是闭环状态问题，不是 action 采样噪声；
3. forced zero-residual 仍有 5 个 true-loss，且 Goal64 的 lost/retained residual
   L2 中位数几乎相同（`0.351/0.352`）；
4. 当前闭环不是“残差大但载体不动”：lost 最近点实际地速约 `2 m/s`，问题是方向
   与 goal 相反，属于 terminal pass-by / recovery，而不是静止卡死。

所以现在不应通过关闭/放大 NoisyNet、重扫 residual scale 或改 reward 权重来救 Gate。

## 6. 决策与算法切换门

`decision = pivot`：停止 estimator/command 的单因素轴，转到预注册的
pre-crossing terminal authority/recovery 审计。下一步只复用现有 rich trace 做
时间窗前移分析，不训练、不扫参数、不打开 held-out。

算法切换提醒（当前均未触发）：

- 若 Goal68 明确证明 optimization/exploration 是主因，才新开预注册 goal，用 SAC
  做同 checkpoint、同 seeds、同评估协议的对照；
- 若 Goal68 明确证明 sample efficiency 是主因，才考虑 REDQ/DroQ；
- 若出现“residual 很大但闭环不动”，才优先查动作参数化、reward 和 terminal
  capture；本 Goal 的闭环在约 `2 m/s` 运动，不符合这条触发条件。

## 7. 算力与验证

- 10 个 candidate 全并行，每 run 40 envs、单线程，墙钟约 20–30 s；
- rich trace 没有改变 dtype/device、动作、reward、终止、reset、seed 或 controller；
- 定向测试 `6 passed`，Ruff 通过；
- 结果 JSON/Markdown 已拉回本地，服务器 trace 留在 goal60 workspace。

下一训练型 goal 的算力策略：按 seed 分配到当时空闲的 GPU 并行，保持每个 seed 的
算法、UTD、replay 比例和评估协议不变；如果要增加 `num_envs`/batch，必须单独预注册
一个算力 screen，固定总 transitions 和 checkpoint 选择规则，不能把 screen 结果混进
正式 Gate。当前 evaluation 已经是 10 路并行、每 run 40 envs，继续提高 envs 会改变
既有 40-seed 协议的随机流，因此本 Goal 不这么做。
