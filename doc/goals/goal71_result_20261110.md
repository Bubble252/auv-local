# Goal71 结果：limiter 生效并改善 tracking，但没有转化为 true retention

**日期**：2026-11-10<br>
**状态**：`TRACKING_IMPROVES_OUTCOME_UNCHANGED`<br>
**预注册**：`doc/goals/goal71_command_rate_limit_control_20261110.md`<br>
**上游**：Goal70 `COMMAND_RATE_INFEASIBLE`

## 1. 结论

正式判定：

```text
default   -> TRACKING_IMPROVES_OUTCOME_UNCHANGED (H71-B)
strict125 -> TRACKING_IMPROVES_OUTCOME_UNCHANGED (H71-B, pitch)
overall   -> TRACKING_IMPROVES_OUTCOME_UNCHANGED
```

- **limiter 确实生效**：default original-lost 的 heading command-rate P90 从
  `1.457` 降到 `0.524 rad/s`，exceed fraction 从 `0.961` 降到 `0.000`；
  strict125 从 `3.489` 降到 `0.524 rad/s`，exceed fraction 从 `0.667` 降到
  `0.000`。
- **H71-B 支持，H71-A 不支持**：default 的 heading tracking error 从
  `0.930` 降到 `0.315 rad`；strict125 的 pitch error 从 `0.596` 降到
  `0.410 rad`。但 true retention 没有净改善。
- default 的 9 个 original-lost 中恢复 `5/9`，但同时新增丢失 `8` 个，
  `true_success_delta = -2`；strict125 的 7 个 original-lost 恢复 `0/7`，
  新增丢失 `3`，`true_success_delta = +1`。
- timeout 与 safety delta 在两个 scenario 都是 `0`；pre-goal RMSE 分别改善
  `1.43%/1.47%`。因此这不是 unsafe，也不是“明显 hurt”（冻结阈值
  `true_success_delta <= -3`），而是 tracking 改善与任务成功脱钩。
- **NoisyNet/residual 不是主导**：zero-residual 在 default 的 true 数从
  `19` 变为 `17`，strict125 从 `11` 变为 `11`；没有 residual 时 limiter
  仍不能改善 true retention。没有 optimization/exploration 或 sample-efficiency
  证据，不启动 SAC/REDQ/DroQ。

## 3. 主结果

pooled over 4 policy checkpoints + zero-residual：

| scenario | baseline true | off true | on true | original lost | recovered orig. | newly lost | true delta | false-success off -> on | RMSE rel. delta |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| default | 70 | 99 | 97 | 9 | 5 | 8 | -2 | 29 -> 31 | -1.43% |
| strict125 | 30 | 43 | 44 | 7 | 0 | 3 | +1 | 17 -> 14 | -1.47% |

`true delta` 是 limiter-on 对 limiter-off 的全量 `recovered_all - newly_lost_all`；
恢复率仍只在 original-lost 子集裁决：

- default：恢复 `5 >= ceil(0.40 × 9) = 4`，但 newly lost `8 > 1`、
  true delta `-2 < +3`，H71-A 失败；
- strict125：恢复 `0 < ceil(0.40 × 7) = 3`，newly lost `3 > 1`、
  true delta `+1 < +3`，H71-A 失败。

所以 limiter 能救回一部分原本丢失的 episode，但同时改变了其他轨迹并制造新丢失；
净 true success 没有增加。

## 4. Tracking：H71-B 成立

crossing 前 1 s，original-lost 子集：

| scenario | side | n | abs heading err | abs pitch err | cmd h p90 | h exceed | actual yaw p90 | abs speed err |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| default | off | 9 | `0.930` | `0.618` | `1.457` | `0.961` | `0.135` | `0.493` |
| default | on | 9 | `0.315` | `0.601` | `0.524` | `0.000` | `0.091` | `0.639` |
| strict125 | off | 7 | `0.364` | `0.596` | `3.489` | `0.667` | `0.125` | `0.169` |
| strict125 | on | 7 | `0.385` | `0.410` | `0.524` | `0.000` | `0.128` | `0.134` |

单位：角度 rad，速度/加速度 m/s 或 m/s²。

- default：heading error 改善 `0.615 rad`，达到 `0.10` 门槛；
- strict125：heading 反而恶化 `0.021 rad`，但 pitch error 改善 `0.186 rad`，
  达到 `0.05` 门槛；
- 2 s 一致性检查比 1 s 弱：default heading error 仍改善 `0.388 rad`；
  strict125 heading 恶化 `0.090 rad`，pitch 只改善 `0.029 rad`。因此
  strict125 的 H71-B 主要由 crossing 前最后 1 s 的 pitch 改善触发，不能外推为
  全窗口持续改善。

执行器与几何侧没有出现新的硬限制：`fin_rate_at_limit_fraction=0`、
`command_reachability_infeasible_fraction=0`、`terminal_phase_fraction=1.0`。
也就是说，限速降低了 command demand 与 tracking error，但没有消除最终 terminal
capture/plane miss 的失败。

## 5. Policy vs zero-residual：NoisyNet 不是主导

| scenario | arm | off true | on true | original lost | recovered orig. | newly lost | true delta |
|---|---|---:|---:|---:|---:|---:|---:|
| default | 4 policy | 80 | 80 | 5 | 4 | 5 | 0 |
| default | zero-residual | 19 | 17 | 4 | 1 | 3 | -2 |
| strict125 | 4 policy | 32 | 33 | 6 | 0 | 2 | +1 |
| strict125 | zero-residual | 11 | 11 | 1 | 0 | 1 | 0 |

这是对“残差是不是被 NoisyNet 主导”的直接负控：

- 完全 zero-residual 时，限速仍不能在 strict125 改善 true retention，default
  反而少 2 个 true；
- policy 的 default 也没有净收益，strict125 只有 `+1`，低于预注册门槛；
- Goal69/70 已经显示 deterministic mean weights、residual/base 在 lost 不更高；
  Goal71 又显示 limiter 改善 tracking 时，zero-residual 仍不跟随改善。

因此当前失败不能归因于 NoisyNet 或 residual 幅度；也不符合“residual 很大但闭环
不动”的情形。闭环在约 `1.9–2.0 m/s` 运动，限速后 command、tracking 和轨迹都
发生了变化，问题在于这些变化没有转化为 true capture。

## 8. 机制解释

这组结果把问题从“command rate 是否可行”推进到“command/tracking 改善为什么不能
转化为 terminal capture”：

1. limiter 把 heading/pitch command rate 限制在 envelope 内，并降低了 command-side
   tracking error；执行器和 reachability 都没有饱和。
2. 但 actual yaw rate 的 P90 在 default 反而从 `0.135` 降到 `0.091 rad/s`，
   strict125 基本不变（`0.125 -> 0.128`）。tracking error 降低主要来自更平滑的
   command，而不是载体获得了更强的 terminal authority。
3. default 的 speed error 从 `0.493` 恶化到 `0.639 m/s`，false-success 增加 2；
   limiter 同时限制 speed/pitch，可能改变了接近轨迹和终端几何。
4. strict125 的 pitch 改善只在最后 1 s 明显，2 s 窗口不稳定；这与 Goal65/68
   的 terminal capture/几何边界问题一致，而不是优化失败。

最便宜的下一个 falsification 应继续复用 Goal71 rich trace，检查 limiter 带来的
tracking 改善究竟在 crossing 后如何改变 `eta`/`p_nav`、terminal offset、speed/height
耦合和 plane-miss 时序。只有该审计再次失败并达到 autoresearch 触发条件，才考虑
controller bandwidth 参数化或新的 terminal-aware 训练 arm。
