## 7. 失败配置与失败原因

最终测量没有失败配置：0 OOM、0 NaN/Inf、0 环境数静默降级、0 异常退出。`scale_report.json` 中 `failures` 为空。

开发过程中出现过两类非最终结果：

1. **安装失败 `pip_check`**：`httpx2 2.16.0` 要求 `idna>=3.18`，与 Isaac Sim 5.0 固定的 `idna 3.10` 冲突。通过约束 `transformers==4.57.6` 并清理 `httpx2 → httpcore2 → truststore` 孤儿链解决。
2. **测量框架假失败 `FAIL_NO_OUTPUT`**：probe 原来在 `simulation_app.close()` 之后写 JSON，而关闭 App 会直接结束进程，导致实际跑完但没有结果文件。将写盘移到关闭 App 之前后，单环境 3/3 通过。

每次启动仍会打印 `Warp CUDA error: cuDeviceGetUuid` 和 `Failed to clone in Fabric`。它们没有阻止环境创建、200 步执行或结果落盘，但属于尚未完全解释的启动告警，保留在远端日志中。

## 8. OceanSim 声呐并行边界结论

IsaacLab 的 1024/4096 环境能力证明的是批量物理调度、CUDA 张量和 Python 训练循环的基础设施上限，**不等于** P1-A OceanSim 声呐也能按同样规模复制。

当前 P1-A 的瓶颈边界是：

- 单相机 `1300 × 200`，每帧约 260,000 像素；1024 环境就是约 2.66 亿像素/帧。
- 每环境 1300 条 `0.1°` 射线；1024 环境是 133 万条射线/帧。
- `OceanSimPointCloudSource` 和 `PointCloudSonarAdapter` 当前都是单环境 Python 对象，包含独立的传感器、位姿写入、点云回读和 NumPy 分箱。
- 主要候选瓶颈依次是 render product/相机复制、GPU→CPU 点云回读、NumPy 扇区聚合、reset 场景重建和 Python 同步调用；不是 DDPG 网络本身。
- 观测契约可以保持，但必须继续使用相同的 130° 前视场、120 m 原始量程、20 m 局部有效视野、13 个 10° 扇区和 17 维观测顺序；训练来源必须写 `analytic_13sector`，OceanSim 评估来源必须写 `oceansim_simplified_pcl`。

详细审计见 `doc/isaaclab/03_OceanSim并行边界审计.md`。

## 9. 是否值得进入 P1 向量化环境开发

**值得，但必须分阶段，不能直接把 Cartpole 的 4096 环境数字当作 P1-A 的容量。**

建议顺序：

1. 先做 16/64 环境的 OceanSim 声呐微基准，测每环境每帧的渲染、`scan()`、GPU→CPU 回读、扇区聚合和 reset 时间。
2. 若 64 环境仍能维持目标决策频率，再实现“解析 13 扇区传感器并行训练 + OceanSim P1-A 评估”的双轨方案。
3. 同步改造 replay buffer、每环境 GRU hidden state、PPER 批量更新和 episode 边界；这些改动先于任何 1024 环境 P1 训练。
4. 只有在 16/64 环境声呐基准通过后，才评估 1024 环境 OceanSim；不能跳过微基准。
