# 局部规划与反应式导航技术栈

记录日期：2026-10-27；冻结更新：2026-10-28；PPO 路线登记：2026-10-29

文档性质：架构与接口草案 v0.5。本文档记录软件分层、数据契约、依赖边界和推荐技术选型，作为 M0 评审和后续实现的依据。

## 1. 设计原则

- 算法核心只依赖标准库、NumPy 和项目内 dataclass/Protocol，不直接依赖 ROS 2、HoloOcean、PVS 或具体控制平台。
- 全局规划器、局部路径规划器、反应式策略、制导、安全滤波和执行器分配是不同职责，不通过一个万能接口混合。
- RL 算法库只负责“观测 → 动作”，不依赖局部规划器、全局规划器或制导实现。
- 轨迹、参考、动作和命令都必须带时间戳、有效期、坐标系和状态语义。
- 训练和评估必须共享 observation builder 与 action adapter，避免预处理漂移。
- 先完成 P1 二维避障课程，再完成 P2 的 2.5D 闭环，最后才考虑完整 3D 和第二个算法；不以空接口和算法数量衡量进度。
- 论文方法、复现解释和工程适配必须分开记录。`MotionArbiter`、`PolicyRolloutPlanner` 等属于我们的工程组件，不冒充论文贡献。
- P1 单环境基线链为 `OceanSim 简化声呐 → DDPG direct-action → SurgeYaw → 二维水平运动学`；DDPG 多环境基线为 `解析 13 扇区 → DDPG direct-action → 张量二维运动学`。2026-10-29 起新增 PPO 链：`解析 13 扇区 → IsaacLab DirectRLEnv → rsl_rl PPO`，其解析训练与课程已通过 G1–G6；OceanSim 50Hz 延迟门未稳定通过，因此 OceanSim 仅保留评估用途。两条多环境路线都最终用 `OceanSim P1-A` 单环境评估，不把解析训练结果冒充 OceanSim 结果。P1 不调用 ALOS、REMUS 控制器或 PVS。P2 评估链固定为 `策略动作 → online rollout → 局部航点/轨迹 → 3D ALOS → REMUS 控制器 → PVS/OceanSim`。
- P1 以二维运动学为权威状态，P2 和最终评估以 PVS 为权威动力学。OceanSim 始终只负责场景和感知，不承担 REMUS 100 的水动力计算，也不把默认 BlueROV 刚体参数当成 REMUS 模型。

## 4. 总体架构

```text
任务与场景
    ↓
GlobalPlanner
    ↓ PlanResult: Trajectory + Certificate + Diagnostics
    │
    ├─ P1 多环境训练链：direct-action
    │    解析 13 扇区 → 17 维观测
    │         ├─ DDPG 基线：张量二维水平运动学
    │         └─ PPO：IsaacLab DirectRLEnv + rsl_rl（解析训练已验证）
    │         ↓
    │    批量 collision / out_of_bounds / reward / auto reset
    │
    ├─ P1 单环境评估链（OceanSim P1-A）
    │    OceanSim 简化声呐 → RangeScan
    │         ↓ ObservationBuilder
    │    ReactivePolicy.act() → [u_dot, r]
    │         ↓ SurgeYaw 动作适配
    │    二维水平运动学 → 权威 State
    │         ↓ 位姿同步
    │    OceanSim 下一帧声呐
    │
    ├─ P2 评估/微调链：online rollout
    │    ReactivePolicy.act() → [u_dot, r] → 局部运动模型
    │         ↓ 局部 Trajectory/航点
    │    ThreeDAlosGuidance → Reference
    │         ↓
    │    Remus100TrackingController → PvsRemus100Backend
    │
    └─ 并行修正模式（后置）
         Guidance 名义 Reference + ReactivePolicy 动作
              ↓
         MotionArbiter → SafetyFilter → MotionExecutor
```

首版不需要仲裁器。P1 训练采用 direct-action 和二维运动学，P2 评估采用 online rollout + ALOS + PVS；两层必须共用观测构建和 `[u_dot, r]` 动作语义，但执行链分开，差异作为独立指标报告。DDPG 是已完成基线和对照；PPO 的解析批量训练、三阶段课程和固定解析评估已通过，OceanSim 端到端评估未通过稳定 50Hz 门，不能写成“OceanSim 多环境训练成立”或“OceanSim 正式评估 PASS”，也不删除 DDPG 的历史结果。并行修正模式保留为后续扩展；若启用，必须记录控制权限切换。OceanSim 只同步位姿并产生传感器数据；P1 以二维运动学为权威状态，P2 以 PVS 为权威状态。OceanSim 的默认 BlueROV 刚体、阻尼和碰撞参数不得写回运动状态。HoloOcean 仅作为并列感知后端保留，不改变主链路的数据契约。

## 6. 核心契约

### 6.1 共享状态与轨迹

复用全局方向的以下对象：

```text
State
Trajectory
Reference
CurrentField
CapabilitySet
ScenarioConfig
PlanResult
RecoveryCertificate
```

坐标和时间约定：

- 世界坐标：NED。
- 体坐标：FRD。
- 角度：rad。
- 时间：仿真时间秒 `t_s`，不使用墙钟时间驱动核心逻辑。
- 四元数：`xyzw`。
- 所有观测、参考、动作必须带 `stamp_s`，必要时带 `valid_until_s`。
- 传感器射线方向必须在体坐标中显式给出，不能只保存一串距离。

### 6.2 局部观测

建议在局部项目中定义感知层对象，而不是继续使用单一 `sonar_ranges_m`：

```python
@dataclass(frozen=True)
class RangeScan:
    stamp_s: float
    sensor_id: str
    frame_id: str
    origin_body_m: FloatArray
    directions_body: FloatArray  # (N, 3)
    ranges_m: FloatArray  # (N,)
    min_range_m: float
    max_range_m: float
    confidence: FloatArray | None = None
```

```python
@dataclass(frozen=True)
class ObstacleTrack:
    track_id: str
    stamp_s: float
    shape_ned: Obstacle
    velocity_ned_mps: FloatArray
    covariance_ned_m2: FloatArray | None = None
    confidence: float = 1.0
    predicted_until_s: float | None = None
```

```python
@dataclass(frozen=True)
class LocalObservation:
    stamp_s: float
    state: State
    scans: tuple[RangeScan, ...] = ()
    tracks: tuple[ObstacleTrack, ...] = ()
    health: Mapping[str, float] = field(default_factory=dict)
    observation_source: str = "unknown"
    previous_action: FloatArray | None = None  # 可选；上一动作 [u_dot, r]
```

单环境基线和最终评估使用 OceanSim P1-A 适配器生成 `RangeScan`；当前多环境训练使用解析 1300 射线生成同一 13 扇区语义。日志中的 `observation_source` 必须分别标明 `oceansim_simplified_pcl` 或 `analytic_13sector`，不能混写。oracle 只用于单元测试、契约测试和故障诊断，不能作为训练或评估感知；使用 oracle 时必须显式标记 `observation_source="oracle"`。算法层始终只消费 `RangeScan` 和 `ObstacleTrack`，不直接接触 OceanSim 原始字典或解析几何内部结构。

首版不照搬论文的 15 维观测。REMUS 100 在既有 `State`、`SimulationSnapshot.actuator_state` 和 `Remus100ControlDiagnostics` 中可提供：

| 数据 | 来源 | 首版用途 |
|---|---|---|
| `position_ned_m` | `State` | 目标距离、相对方位、rollout 起点 |
| `quat_xyzw` | `State` | 艏向、俯仰、姿态相关特征 |
| `linear_velocity_body_mps` | `State` | 主要使用纵向速度 `u`，`v/w` 可选 |
| `angular_velocity_body_rps` | `State` | 主要使用艏摇角速度 `r`，`p/q` 可选 |
| 舵角、艉水平舵、RPM | `SimulationSnapshot.actuator_state` | 诊断、平滑性和执行器约束 |
| 期望/实际相对速度、速度误差、航向/俯仰误差 | `Remus100ControlDiagnostics` | 可选扩展，不进入第一版最小观测 |
| 当前六自由度加速度 | `PvsRemus100Backend.derivative_nu_dot()` | 动力学诊断；不在训练核心中默认使用 |

第一版最小观测为：

```text
13 个前视声呐扇区距离（水平视场 130°，每 10° 一簇）
+ 目标距离
+ 目标相对艏向角
+ 当前纵向速度 u
+ 当前艏摇角速度 r
= 17 维基础观测
```

13 个扇区不是 360° 全向声呐。论文使用 130° 前视声呐，每 10° 聚类一次，得到 `[d0..d12]`；本项目按相同视场实现，不把后向或侧后向扇区偷塞进这 13 维输入。

首版归一化固定为：扇区距离除以 P1 局部有效量程 `20 m` 并裁剪到 `[0, 1]`；原始 `RangeScan` 仍保留 `120 m` 物理量程，但超过 `20 m` 的回波在 P1 观测中饱和为 `1.0`。目标距离除以当前 episode 的初始目标距离并裁剪到 `[0, 1]`；目标相对艏向除以 `π`；`u` 按 REMUS 最小/最大航速缩放到 `[0, 1]`；`r` 除以 REMUS 最大艏摇角速度。训练、rollout 和评估共用同一 builder 与同一归一化参数。

`previous_action` 是 `LocalObservation` 的可选字段，默认不作为 Actor 的强制输入。论文的 Actor 输入是 15 维，Critic 额外接收上一动作而成为 17 维；我们的 DDPG 适配器按相同方式实现“Actor 17 维基础观测、Critic 可加 2 维上一动作”，但通用 `LocalObservation` 不强制依赖它。`RangeScan.frame_id` 固定为 `body_frd`，局部请求中的轨迹窗口固定为 `world_ned`。

#### 6.2.1 OceanSim 声呐路线与 P1-A 冻结参数（2026-10-28）

OceanSim 的 `ImagingSonarSensor` 提供两种可用前端：几何点云（`scan_data['pcl']`、`normals`、`viewTransform`）和距离-方位强度图（`sonar_data`）。两者都不是论文的 13 维距离数组。P1 单环境基线和最终评估选择 **P1-A 几何点云路线**：复用 OceanSim 声呐相机的几何前端，不经过强度成像后端，再把点云聚合为 13 个水平扇区。当前多环境训练改用同一射线的解析几何求交，见 `6.2.2`。两种来源都必须明确不是论文 512 波束强度声呐的严格复现。

三条路线的边界：

| 路线 | 用途 | 原始输入 | 输出 | 状态 |
|---|---|---|---|---|
| P1-A | P1 单环境基线、配对标定与最终评估 | OceanSim 几何点云、外参、法向 | 1300 条 0.1° 射线 → 13 个 10° 扇区 | 已冻结 |
| P1-B | 感知消融 | OceanSim `sonar_data` 强度图 | 阈值/聚合为 13 个距离 | 后置；不进入 P1 主表 |
| P5 | 高保真感知、VLN/世界模型预研 | 原生强度图、点云、语义图 | 独立 `ObservationSpec` 与编码器 | 独立轨道；不修改 P1 契约 |

**P1-A 冻结参数**

| 项目 | 冻结值 | 说明 |
|---|---|---|
| 传感器物理量程 | `0.2–120 m` | 原始 `RangeScan.max_range_m=120.0`，用于日志、P2 和上层接口 |
| P1 局部有效视野 | `20 m` | 观测与 R2 使用；超过 20 m 饱和，不丢原始 120 m 数据 |
| 水平视场 | `130°` | 与论文兼容观测一致 |
| 水平扇区 | 13 个，每个 `10°` | Actor 17 维输入不变 |
| 点云相机分辨率 | `1300 × 200` | 水平/垂直约 `0.1°`；水平 1300 px，垂直按 130°:20° 比例计算 |
| `RangeScan` 射线 | 1300 条，`0.1°` 一条 | 先按 0.1° 取最近点，再压成 13 个 10° 扇区 |
| 垂直切片 | 传感器平面 `±0.5 m` | P1 障碍物定义为贯穿该切片的竖直棱柱；避免地面、门框顶梁误触发 |
| 扇区聚合 | 每个 0.1° 取最近点，每个 10° 取最小距离 | 无回波填 `120 m`；观测层截断为 `20 m` |
| 安装位置 | 艏部 `[0.8, 0, 0] m`，无俯仰 | 工程初值，避免相机位于艇体内部；不是论文参数 |
| 噪声 | P1-A 基线与评估关闭 | 先得到确定性几何基线；噪声/dropout 作为后续独立消融 |
| 更新方式 | 每个 RL step 取新帧 | RL 周期 `0.2 s`；`valid_until_s=stamp_s+0.5 s` |
| 过期处理 | 超过 `0.5 s` 直接报错 | 不静默复用旧帧；P1 不把传感器故障当策略挑战 |
| 空场景 | 全部填 `120 m`，`scan_valid=1`、`points=0` | 不能把“没有回波”误判为传感器失败 |
| 集成方式 | 第一版同进程同步调用 | 吞吐不足再评估独立服务；不先引入 RPC |
| 日志来源 | `observation_source="oceansim_simplified_pcl"` | 必须能与 `oracle` 明确区分 |
| 论文表述 | “OceanSim 几何简化声呐” | 不得写成 512 波束严格复现或 Oculus 原机复现 |

**为什么采用 120 m / 20 m 双尺度**

- 120 m 是传感器物理量程，保留给日志、P2 闭环和未来全局/分层接口。
- 120 m 直接用于 P1 观测会把近场压扁：5 m 障碍只有 `5/120=0.042`，1 m 只有 `0.008`，网络难以区分近处距离。
- 120 m 直接用于 R2 会让 `0.7 × 120 = 84 m` 就触发近障碍惩罚，远处 80 m 目标支配局部避障奖励。
- 因此 P1 观测 builder 的 `max_range_m` 与 R2 的 `d_max` 都取 `20 m`；原始 `RangeScan` 仍保留 120 m。P2/全局层若需要 120 m 观测，必须使用独立的 `ObservationSpec`，不能修改 P1 的 17 维契约。

**几何处理流程**

1. OceanSim 仿真 tick 推进后，将二维运动学/PVS 的权威位姿同步到声呐相机。
2. 调用 `scan()` 获取 `pcl`、`normals`、`viewTransform`；不可用时显式报错。
3. 用外参把点云变换到体坐标 FRD，过滤自身艇体、`[0.2, 120] m` 之外、水平视场 `±65°` 之外和垂直切片 `±0.5 m` 之外的点。
4. 按 `0.1°` 分箱，每个方位取最近点水平距离；无点填 `120 m`。
5. 构造 `RangeScan`：`frame_id="body_frd"`、`origin_body_m=[0.8,0,0]`、1300 个 `directions_body`、`stamp_s`、`valid_until_s` 和 `health`。
6. `ForwardSectorObservationBuilder` 将 1300 条射线压成 13 个 10° 扇区，并把距离截断到 20 m；训练、rollout 和评估共用该 builder。

**P1-A 的明确限制**

- 点云来自 OceanSim 声呐相机的几何前端，不是 `sonar_data` 强度回波；没有反射率、多回波和真实声呐噪声。
- 0.1° 采样是为了 120 m 处 1 m 级目标不被漏检；它不意味着 OceanSim 具备 0.1° 的真实声学分辨率。
- OceanSim 的 `scan()` 依赖语义标签；空场景或未标注对象可能没有点云。适配器必须区分“空回波”和“传感器失败”，并记录 `health`。
- P1 的碰撞/越界仍由独立二维几何判定；声呐只提供观测，不能作为碰撞真值。
- P1-B 强度图路线和 P5 原生感知路线都不得修改 P1-A 的默认 17 维契约；结果必须分表。

**M4 首版 DDPG 硬要求（2026-10-27 用户确认）**

首版不是普通 DDPG 写完后再外挂模块，而是在网络、回放和训练循环中同时实现：

- **Noisy Network 参数探索**：Actor 和 Critic 都使用可学习参数噪声层，`w = μ_w + σ_w ⊙ ε`，`σ_w = softplus(ρ_w)`，`μ` 与 `ρ` 同时接收梯度；`ε` 使用标准 NoisyNet factorized Gaussian noise。主训练不使用动作空间高斯/OU 噪声，评估时切换为均值权重；动作噪声只保留为基线消融。
- **GRU 时序记忆**：Actor 与 Critic 都带独立的 GRU 隐藏状态，训练样本按连续 `10` 步序列回放，不能跨 episode 拼接；在线 rollout 使用策略状态的 clone/snapshot，不能推进或污染真实策略记忆。
- **PPER 比例优先回放**：使用 SumTree 存优先级 `p_i = |δ_i| + ε`，采样概率 `P(i) = p_i^α / Σ_j p_j^α`，重要性采样权重 `w_i = (N·P(i))^{-β} / max_j w_j`；每次 critic 更新后刷新优先级，`β` 按预注册计划退火。
- 三项分别提供独立开关，默认全开；必须能运行 vanilla DDPG、+Noisy、+GRU、+PPER 和完整组合的消融，而不是只能全有或全无。
- checkpoint 必须保存网络结构、Noisy 参数、GRU 隐藏维度、history length、PPER 参数、观测/动作规格、归一化统计和代码版本。

**P1 奖励 v2 技术边界（2026-10-28 用户确认）**

奖励 v2 与论文复现奖励分开配置。P1 的奖励 v2 必须同时包含四项：目标进度、基于全艇体 clearance 的障碍距离势函数、参考速度惩罚和归一化动作平滑；四项都必须有独立日志，并通过 R5 全开、R6–R9 leave-one-out 评价贡献。终端奖励在当前 P1 仍保留 `-80` 碰撞/越界、`+50` 到达目标，不能因参考图使用其他数值而静默替换。

HER、TTC、ICM/RND 本轮后置：P1 是固定目标的静态障碍课程，不引入 goal relabeling；TTC 等动态障碍场景建立后再加入；ICM/RND 会改变探索奖励的非平稳性，必须等基础策略和奖励 v2 稳定后单独立项。任何后置组件都不能进入当前 P1 主表。

论文报告的 `4.4 h vs 9.6 h` 和 `88.7% vs 56.7%` 只作为参考结果，不作为本项目的复现承诺；本项目必须报告自己的训练曲线、成功率和计算成本。

#### 6.5.1 张量向量环境与向量化 DDPG（2026-10-28）

P1 的二维运动学、碰撞、越界、奖励和解析扇区都可以表示成批量张量运算，因此 DDPG 路线不需要依赖 IsaacLab 或 OceanSim 的场景复制能力。DDPG 首版采用自研 PyTorch 张量向量环境，而不是把 IsaacLab Cartpole 的 `num_envs` 直接套到 P1；PPO 候选路线改用 IsaacLab `DirectRLEnv`，见 6.5.2。

```text
N × State（batch 维）
  → N × 17 维观测
  → 单个 Actor，每环境独立 history / GRU hidden / NoisyNet 噪声
  → N × [u_dot, r]
  → 批量 10 × 0.02 s 积分、碰撞、越界、奖励、自动 reset
  → 张量化 sequence replay / PPER 更新
```

必须满足的语义：

- 每个环境有独立 `env_id`、`episode_id`、`episode_step`、状态、终止原因和随机种子流。
- 一个 episode reset 只清空该环境的 history 和 hidden；不能污染其他环境。
- Replay 的连续序列只能来自同一环境、同一 episode；自动 reset 后不得把新观测写回上一条 transition。
- `terminated` 的 bootstrap 为 0；`truncated` 是否 bootstrap 必须由配置显式决定并测试。
- NoisyNet 噪声按环境独立采样；PPER 的 add、sample 和 update priorities 必须支持 batch，beta 按梯度步更新。
- 不是每一步都自动做一次梯度更新就算正确：必须记录 `env_steps`、`gradient_steps`、`update_to_data_ratio`，避免环境数增加后无意稀释学习信号。
- 默认保持旧单环境的更新比例 `update_to_data_ratio=1.0`；若要改变，必须作为预注册消融，并同时报告样本吞吐和梯度更新吞吐。
- checkpoint 必须与现有 Actor/Critic 结构兼容，才能加载到 OceanSim 单环境评估入口。

吞吐指标必须同时报告 `env_steps/s`、`control_steps/s`、`gradient_steps/s`、P50/P95 控制步耗时和显存；只报告 env steps/s 会掩盖更新成本和策略决策频率。环境数通过语义测试、隔离测试和端到端吞吐门后才能扩大。

### 6.6 Policy Rollout 适配器与评估链

把一个闭环策略转换成局部路径，必须运行一个短时域预测模型。这是“Actor 动作”到“局部规划器对外航点/轨迹”的显式边界，也是首版评估链；训练阶段不以这条路径作为唯一观测来源：

```text
真实快照中的当前状态
  ↓
构建观测 → policy.act(observation)
  ↓ [u_dot, r]
局部运动模型积分 step_s → 下一状态/局部航点
  ↓
用预测状态、障碍和声呐模型构建 predictive observation
  ↓
重复到时域终点，输出局部 Trajectory
```

时序定义：

- 每个局部决策周期从真实快照重规划，不在上一周期预测状态上继续累加。
- rollout 内部每个 `step_s` 重新调用一次策略，而不是重复同一个动作。
- rollout 时域结束或触发碰撞/越界/目标到达时停止。
- 输出轨迹交给现有 `ThreeDAlosGuidance` 跟踪；ALOS 和控制器按真实仿真时间运行，不按 rollout 时间运行。
- 本周期轨迹在下一次决策前是 ALOS 的跟踪对象；新轨迹必须重新映射时间戳，不能造成时间倒退。

首版工程默认值如下。这些是待 M2/M5 验证的实现参数，不是论文参数，也不是成功阈值：

| 参数 | 初始值 | 说明 |
|---|---:|---|
| `rollout.horizon_s` | 2.0 s | 在 REMUS 1.0–2.5 m/s 下对应约 2–5 m 前视路径 |
| `rollout.step_s` | 0.2 s | rollout 内部策略与积分步长；10 次策略调用对应论文 37.9 ms/次约 379 ms |
| `rollout.replan_period_s` | 0.5 s | 从真实快照刷新局部路径的周期 |
| `rollout.max_path_length_m` | 5.0 m | 防止策略原地绕圈或速度过低时无限展开 |
| 策略调用 | 每个 rollout 步一次 | 形成闭环动作序列，不是固定动作重复 |
| 局部深度来源 | `route_window` / 全局参考 | DDPG 不决定深度，ALOS 负责垂直跟踪 |

论文没有明确给出仿真步长 `h`、rollout 时域、重规划周期或航点间距，因此上表不是论文原值。2.0 s 时域来自 REMUS 速度范围 1.0–2.5 m/s（对应 2–5 m 前视路径）；0.2 s 步长和 0.5 s 重规划周期来自论文 37.9 ms 单步规划成本与 512 波束声呐 27 Hz 的实时性上限，属于待 M2/M5 实测校准的工程取值。

建议接口：

```python
@dataclass(frozen=True)
class RolloutConfig:
    horizon_s: float
    step_s: float
    replan_period_s: float
    max_path_length_m: float
    stop_on_collision: bool
    model_id: str
    clip_actions: bool = True
    inherit_depth_from_route: bool = True


class PolicyRolloutPlanner:
    def __init__(self, policy: RLPolicy, model: LocalMotionModel, config: RolloutConfig): ...

    def reset(self, *, seed: int = 0) -> None: ...

    def plan_local(self, request: LocalPathRequest) -> LocalPathPlan: ...
```

适配器必须满足：

- 在预测副本上运行，不能修改在线策略的 GRU/RNN 记忆；或提供显式的 `snapshot/restore` 机制。
- 每次 rollout 记录模型版本、时域、步长、动作限幅、终止原因和计算耗时。
- 预测观测必须由环境模型、障碍模型和传感器模型共同生成，不能只在当前声呐帧上重复动作。
- rollout 只生成 `LocalPathPlan`，不替代 `SafetyFilter`，也不能把预测轨迹直接视为安全。
- 预测轨迹与真实闭环轨迹分开保存，报告中必须标明哪一条是模型预测、哪一条是 PVS/OceanSim 实际执行。

### 6.7 制导

复用全局方向的 `Guidance` Protocol 和 `ThreeDAlosGuidance`：

```python
class Guidance(Protocol):
    def guide(self, state: State, trajectory: Trajectory, t_s: float) -> Reference: ...
```

首版 ALOS 跟踪 `LocalPathPlan.trajectory`。它使用既有的 `ThreeDAlosGuidance`，输出 `Reference`；`Remus100TrackingController` 继续把 `Reference` 转成 `Remus100ActuatorCommand`。并行修正模式下才需要仲裁器协调 ALOS 与反应式动作。

### 6.8 仲裁、安全与执行

```python
class MotionArbiter(Protocol):
    def arbitrate(
        self,
        nominal: Reference,
        reaction: Reaction | None,
        request: ReactiveRequest,
    ) -> ControlProposal: ...


class SafetyFilter(Protocol):
    def filter(
        self,
        proposal: ControlProposal,
        context: SafetyContext,
    ) -> SafeCommand: ...


class MotionExecutor(Protocol):
    def execute(
        self,
        state: State,
        nominal_reference: Reference | None,
        command: SafeCommand,
        capability: CapabilitySet,
    ) -> ActuatorCommand: ...
```

`MotionArbiter` 不属于参考论文。首版复现把 DDPG 放在 ALOS 上游，只启用单一路径，不使用仲裁器；只有在线联调“反应式策略 + 名义制导”时才启用它。
